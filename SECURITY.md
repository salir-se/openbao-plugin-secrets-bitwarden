# Security policy

This plugin handles a Bitwarden master password, an OpenBao token and the
secrets it copies between the two. Please report anything that could expose
them.

## Reporting a vulnerability

Use GitHub private vulnerability reporting:

1. Go to the repository's **Security** tab.
2. Choose **Report a vulnerability**.
3. Describe the issue, the affected version or commit, and how to reproduce it.

Direct link:
<https://github.com/salir-se/openbao-plugin-secrets-bitwarden/security/advisories/new>

Do not open a public issue, pull request or discussion for a suspected
vulnerability, and do not include real credentials in a report.

Write the report in your own words and include reproduction steps. If any part
of it was generated by AI, label that part. See
[CONTRIBUTING.md](CONTRIBUTING.md#ai-assisted-contributions).

This is a small project maintained on a best-effort basis. We will acknowledge
reports as soon as we can and keep you informed through the advisory thread.
Once a fix is released we publish the advisory and credit the reporter unless
asked not to.

## Supported versions

Bug and security fixes are made for the latest minor series only, unless a
release announcement states otherwise. Older minor series and pre-releases
(`-beta`, `-rc`) do not receive fixes. The project is pre-1.0; upgrade to the
latest release to get a fix.

## Scope

In scope:

- the plugin code in this repository
- the release artifacts published from this repository

Out of scope: vulnerabilities in OpenBao, Bitwarden or Vaultwarden themselves.
Report those to the respective projects.

## Known limitations

These are documented behaviours of the current code, not undisclosed
vulnerabilities. Improvements are welcome through normal issues and pull
requests.

**Access control**

- Source secrets are read with the configured `bao_token` whenever it is set.
  The caller's own token and policies are not consulted for the source path.
  Anyone who may write `roles/*` and trigger a sync on the mount can therefore
  copy any path that token can read into a collection. Give `bao_token` a
  narrowly scoped, read-only policy and restrict who may write `roles/*`.
- `read status` and `read sync/<name>` make outbound requests to the Bitwarden
  server (a reachability probe and login, and an item fetch, respectively).
  Grant read access to those paths with that in mind.

**What gets written to the vault**

- Every key of the source secret that the role does not map to an item field
  is synced as a visible text custom field. Custom fields are not marked
  hidden.
- When a role has no stored `cipher_id`, existing items are matched by name
  (within the organization, when one is configured). The most recently
  revised match is overwritten and all other items with the same name are
  permanently deleted. Use dedicated collections and item names that cannot
  collide with manually managed items.
- If updating an item fails for any reason, the plugin falls through to
  creating a new item and links the role to it. The previous item is left in
  place.
- Concurrent syncs of the same role are not serialised.

**Transport and cryptography**

- `url` accepts `http://`. Nothing enforces TLS toward the Bitwarden server.
- A private CA for the Bitwarden server must be in the system trust store of
  the host or container running OpenBao. There is no option to supply one.
- TLS verification toward `bao_addr` is on by default and can be switched off
  with `bao_tls_skip_verify`.
- Only PBKDF2-SHA256 accounts are supported. Argon2id accounts are rejected at
  login.
- The PBKDF2 iteration count is taken from the server's prelogin response and
  is not bounded by the plugin, neither below nor above.
- The account cannot use two-step login; the plugin sends no second factor.

See "Security considerations" in the [README](README.md#security-considerations)
for what the plugin stores and can access.
