# Contributing

Thanks for considering a contribution. This project is small and maintained on
a best-effort basis, so focused issues and pull requests are the easiest to
act on. If you are unsure whether something fits, open an issue and ask first.

The policy below is modelled on OpenBao's contribution rules
([community guide](https://openbao.org/community/contributing/),
[CONTRIBUTING.md](https://github.com/openbao/openbao/blob/main/CONTRIBUTING.md)),
scaled down to a single-plugin project and written in our own words. It
deviates from OpenBao in one place, [AI-assisted contributions](#ai-assisted-contributions),
and says so there.

By participating you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Contributions are accepted under the project's [MIT license](LICENSE).

**Security problems do not belong in public issues or pull requests.** Use
private vulnerability reporting as described in [SECURITY.md](SECURITY.md).

## Source-available and copyleft licence policy

This rule applies to every contribution from now on.

Contributions must not use or copy from source code that is under a
source-available licence, including the Business Source License 1.1. That
specifically covers every repository in HashiCorp's GitHub organisation,
HashiCorp Vault included. When you implement behaviour that Vault also has,
work from OpenBao's own code and documentation, not from Vault's.

The same applies to code this project cannot relicense under MIT:

- Bitwarden code under the Bitwarden License
- GPL- or AGPL-licensed servers and clients. Vaultwarden is AGPL-3.0 and the
  Bitwarden clients are GPL-3.0.

Do not copy or translate code from those projects. Implement from public
protocol and API documentation and from behaviour you observe against a
running server.

## Developer Certificate of Origin (DCO)

Every commit must carry a `Signed-off-by` line. By adding it you agree to the
[Developer Certificate of Origin](https://developercertificate.org/) for that
contribution: you confirm that you have the right to submit it under the
project's licence.

```bash
# Sign off a new commit
git commit --signoff -m "fix: describe the change"

# Add a sign-off to the last commit
git commit --amend --signoff

# Sign off every commit on your branch
git rebase --signoff main
```

This appends a line such as:

```
Signed-off-by: Alex Smith <alex@example.com>
```

A DCO sign-off is not the same as cryptographic commit signing with GPG or
gitsign. Signing a commit that way does not replace the sign-off line.

The `DCO sign-off` job in CI checks every commit of a pull request for the
trailer. Commits without it are not merged.

## AI-assisted contributions

**This section differs from OpenBao's policy.** OpenBao does not accept
AI-generated code, pull-request descriptions or issues. This repository cannot
truthfully adopt that rule: parts of it, at minimum the unit tests, the
documentation and the CI configuration prepared for the first public release,
were produced with generative AI assistance under maintainer direction.

AI-assisted contributions are accepted here only under these conditions:

- **Disclose it.** Tick the "Generative AI was used" box in the pull-request
  template's Acknowledgements section and say in the description which parts
  it covers.
- **Review and understand it.** The person submitting must have read, tested
  and understood every line, and must be able to explain and maintain it.
- **Sign it off.** The submitter's DCO sign-off covers the AI-assisted parts
  too. The human takes responsibility for the provenance of the contribution,
  including that it does not reproduce code under the licences listed above.

For issues and security reports, write in your own words and include
reproduction steps. Using AI to help you debug or understand a problem is
fine. If any text you post was generated by AI, label it as such. Reports that
are plainly unreviewed AI output may be closed without a detailed reply.

Because of this difference, **do not submit code from this repository to
OpenBao's own repositories** where doing so would violate their rule against
AI-generated contributions.

## Reporting issues

- Test against the latest release first. The bug may already be fixed.
- Give steps to reproduce, with the expected and the actual result. Paste
  them as text, not screenshots.
- Include the plugin version (release tag or commit), the OpenBao version, and
  the server on the other side (Vaultwarden or Bitwarden) with its version.
- Include the relevant OpenBao and plugin log lines. The plugin logs to the
  OpenBao server log. Remove passwords, tokens and any IDs or hostnames you
  consider private before posting.
- Security issues go to private vulnerability reporting only. See
  [SECURITY.md](SECURITY.md).

Reports from people running the plugin against the official Bitwarden server
are especially welcome, whether it worked or not. That combination is
currently untested.

## Pull requests

- Reference an existing issue, and open one first if none exists. Trivial
  fixes such as typos are exempt.
- Describe what the change does, how it does it, and why you chose that
  approach.
- Include unit tests for the change. Existing tests must pass.
- Keep unit-test coverage above 95% (see below).
- Fill in the Acknowledgements section of the pull-request template, including
  the AI-assistance choice (tick exactly one).
- Keep each pull request to one change. Separate refactoring from behaviour
  changes.
- Update the documentation in the same pull request. Every path, field,
  default and behaviour described in `README.md` and `docs/` must match the
  code.
- Never include real credentials, hostnames or IDs in code, tests, fixtures or
  documentation. Use `example.com` and placeholders.

A pull request is merged when CI is green, review comments are resolved, and
one maintainer has approved it.

Changes to the cryptography in `crypto.go` get extra scrutiny. Explain the
protocol behaviour you are implementing, cite the public documentation, and
add test vectors where possible.

## Changelog entries

Changes that users will notice need an entry in [CHANGELOG.md](CHANGELOG.md)
under `Unreleased`, written as a full sentence, in one of the categories
OpenBao uses:

| Category | Use for |
|----------|---------|
| Features | New functionality |
| Improvements | Enhancements to existing functionality |
| Changes | Changes that need action from the operator, including breaking changes |
| Deprecations | Functionality scheduled for removal |
| Bugs | Bug and security fixes |

Documentation updates, test changes and refactors do not need an entry.

## Development setup

You need the Go version named in `go.mod` or newer, `make`, and Docker with
Compose v2 for the integration and end-to-end tests.

```bash
make build             # static plugin binary (CGO_ENABLED=0)
make test              # unit tests, no external services
make cover             # unit tests with the coverage gate
make test-integration  # OpenBao + Vaultwarden in Docker
make e2e-test          # plugin inside a real OpenBao, verified with the bw CLI
make e2e-up            # same environment, left running; make e2e-shell, make e2e-down
make lint
make clean
```

### Layout

| Path | Contents |
|------|----------|
| `cmd/openbao-plugin-secrets-bitwarden/` | Plugin entry point |
| `backend.go` | Backend factory, client cache, periodic sync |
| `path_*.go` | One file per API area: config, status, roles, sync, collections, folders |
| `client.go` | HTTP client for the Bitwarden API |
| `crypto.go` | Key derivation and item encryption |
| `*_test.go` | Unit tests |
| `integration_test.go`, `testhelpers_test.go` | Integration tests, behind the `integration` build tag |
| `scripts/integration-test.sh`, `docker-compose.test.yml` | Integration test harness |
| `e2e/` | End-to-end environment and suite ([docs/e2e.md](docs/e2e.md)). `e2e/bootstrap` is Go behind the `e2e` build tag, so it stays out of the coverage gate |
| `docs/` | Reference and operations documentation |

### Tests and the coverage gate

- New code needs tests. A change in behaviour needs a test that fails without
  it.
- Unit-test coverage must stay above 95%. Run `make cover` before you push. It
  runs the unit tests and fails if coverage is below the threshold.
- CI runs the same gate on every pull request. A pull request that drops
  coverage below the threshold fails and will not be merged.
- Unit tests must not need network access or running services. Mock the
  Bitwarden API with `net/http/httptest`, as the existing tests do.
- Changes to `client.go`, `crypto.go` or the sync flow should also pass
  `make test-integration`. It starts throwaway OpenBao and Vaultwarden
  containers on ports 18200 and 18080 and removes them afterwards.
- Changes to paths, sync behaviour, organization handling or anything the
  `bao` CLI shows should also pass `make e2e-test`. It builds the plugin into
  an OpenBao image, runs it against Vaultwarden over HTTPS and checks the
  results with the Bitwarden CLI as a read-only organization member. It uses
  ports 28200 and 28443 on localhost and takes about six minutes. See
  [docs/e2e.md](docs/e2e.md).

## Releasing

Maintainers only. Releases follow semantic versioning and are published by
GitHub Actions from `v*` tags. While the version is 0.x, breaking changes bump
the minor version and are listed under "Changes". New features target `main`;
bug and security fixes are backported to the `release/<major.minor>` branch of
the latest minor series. The checklist is in
[docs/releasing.md](docs/releasing.md).
